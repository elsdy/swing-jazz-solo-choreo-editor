# 로드맵

이 문서는 앞으로 무엇을 만들 것인지와, 그것을 받아들이기 위해 지금 어떤 자리를 비워 두었는지를 적는다. 새 기능을 시작하기 전에 여기서 전제와 미결정 사항을 확인한다. 완료된 것은 [개발 이력](HISTORY.md)으로 옮긴다.

## 큰 그림

안무 편집기는 지금 "격자에 동작을 배치하는 도구"다. 앞으로는 **연습 도구**가 된다 — 안무 옆에 영상을 두고, 카운트와 재생 위치를 맞춰 보고, 연습이 쌓이는 동안 무엇이 나아졌는지 되돌아본다.

그 방향이 구조에 건 요구는 셋이다.

- 안무 격자의 좌표와 영상의 시각이 **한 축 위에서** 만나야 한다.
- ~~영상 시퀀스를 다루는 엔진은 **다른 프로젝트에서 통째로 들어온다.**~~ 2026-09-09 에 그 프로젝트를 실제로 열어 보고 전제가 틀렸음을 확인했다(아래 백로그 2번). 가져올 수 있는 것은 ffmpeg 래퍼 297줄이고, 그것도 서버를 도입해야 쓸 수 있다.
- 프로젝트가 시간축을 갖는다 — 한 안무의 여러 버전과 연습 기록이 함께 저장된다.

- 재생 위치는 도메인 상태에 들어가지 않는다 — `Undo` 에 남지 않고 안무표를 다시 그리지도 않는다([아키텍처](ARCHITECTURE.md#휘발성-렌더-채널-재생-헤드는-dirty-를-타지-않는다)의 채널 B).
- 데스크톱은 안무표 오른쪽, 1040px 이하에서는 안무표 위. **DOM 은 움직이지 않고 CSS 만 바꾸므로** 창을 좁혀도 재생이 끊기지 않는다.
- `전체 초기화(링크 포함)` 이 영상 소스와 템포도 함께 지운다. 링크를 비우면서 영상만 남으면 링크바와 패널이 갈라지기 때문이다 — `Undo` 한 번이면 배치·링크와 함께 돌아온다.

이번 묶음에서 내린 설계 결정(다음에 같은 자리에서 재사용한다):

- **"지금 어느 블록인가"는 상태가 아니라 관측값이다.** 재생 위치의 함수이므로 store 에 넣지 않고 재생 헤드와 같은 휘발성 채널이 클래스만 토글한다. 다만 헤드가 같은 칸에 멈춘 채 블록이 다시 그려지는 경우가 있어, 렌더러가 "네 캐시가 낡았다"고만 알리는 `invalidate` 훅을 둔다.
- **동작마다 시각을 저장하지 않고 템포 지도를 둔다.** 배치별 시각은 격자 좌표와 시간이 두 진실이 되어 배치를 옮기면 어긋난다. 대신 앵커를 점 하나로 보고 보정점을 더해 구간별 선형으로 잇는다 — 카운트↔초 변환이 한 곳(`domain/tempo.js`)에 있어 헤드·점프·하이라이트가 전부 자동으로 따라온다. 보정점이 없으면 옛 선형식과 한 자리도 다르지 않다(테스트가 등호로 단언).
- **파일 소스는 파일명 + 보관 루트 기준 상대 경로만 저장한다.** blob URL 도 절대 경로도 파일에 넣지 않는다. 경로 모양(`<subdir>/<프로젝트>/<파일>`)을 서버 방식과 브라우저 폴더 방식이 똑같이 쓰므로 프로젝트 파일이 어느 쪽에서도 열린다.
- **LLM 은 서버가 부르고, 답은 스키마로 받아 두 번 검증한다.** 브라우저에 키를 둘 수 없고 로컬 LLM 은 CORS 에 막히므로 중계는 서버 몫이다. 모델에게는 구조화 출력(JSON 스키마)을 요구하고, 그래도 서버가 한 번(숫자·이름), 도메인이 또 한 번(격자 클램프·이름 매칭) 검증한다 — 모델의 답은 입력이지 명령이 아니다. "다듬기"를 한 단 따로 둔 이유는 음성 인식 오류와 줄임말을 사람이 고칠 자리를 만들기 위해서다.
- **서버는 파이썬 표준 라이브러리로만 만든다.** 로드맵이 서버를 미룬 이유가 pip 환경과 두 번째 런타임의 비용이었으므로, 그중 앞의 것은 내지 않는다. 서버와 앱 사이는 HTTP 뿐이고, 서버가 없으면 앱이 스스로 브라우저 방식으로 떨어진다 — 정적 호스팅이 여전히 유효하다.

### 전체 초기화한 링크의 되돌리기 (2026-09-07)

[일부러 두고 온 것](deviations.md)의 `다음에 고칠 후보` 에서 링크 건을 닫았다. 남은 큰 건이던 리사이즈의 충돌 규칙은 아래 항목에서 닫혔다.

- `전체 초기화` 뒤 `Undo` 한 번으로 배치와 링크가 함께 돌아온다. 복원한 링크는 localStorage 에도 되쓰므로 새로고침해도 남는다.
- 상태의 정의를 한 곳으로 모았다 — `UNDO_FIELDS` 와 `DOC_FIELDS` 가 같은 집합이 되어, 파일과 undo 가 같은 것을 상태로 본다([개발 원칙 D-4](PRINCIPLES.md#d-4)).
- 링크 편집이 히스토리 단계를 만든다. 커밋 지점은 값이 확정되는 여섯 자리로 한정했다 — 입력 중(`input`)과 제목 조회 응답에는 걸지 않는다.
- 버튼 라벨이 `전체 초기화(링크 포함)` 이 됐다. 정리 범위를 넓힌 것과 그것을 알리는 문구가 이제 같은 자리에 있다([개발 원칙 R-4](PRINCIPLES.md#r-4)).
- 골든 150개는 undo/redo 를 다루지 않아 이 변경을 지켜 주지 못한다. 안전망은 `tests/unit/domain.test.mjs` 의 단위 테스트 38개다.

### 겹침 충돌 규칙 통일 (2026-09-07)

[일부러 두고 온 것](deviations.md)의 `특히 걸리는 하나` 를 닫았다. 사용자가 확인 없이 데이터를 잃는 부류는 이제 없다.

- 오른쪽 손잡이로 블록을 늘려 다른 블록과 겹쳐도 그 블록이 지워지지 않는다. 늘린 블록이 빈 층을 찾아 아래로 내려간다.
- 놓기·이동·복사·리사이즈 네 조작이 같은 충돌 규칙을 쓴다([개발 원칙 D-2](PRINCIPLES.md#d-2)). `boardOps.js` 의 네 정책 상수에서 `keepLane` · `overwriteSameLane` 이 넷 다 `true` 가 아닌지를 단위 테스트가 직접 단언한다.
- **규칙을 먼저 정하고 코드는 플래그 두 개만 뒤집었다**([개발 원칙 D-1](PRINCIPLES.md#d-1)). 다섯 달을 미결로 있던 "덮어쓰는가 쌓는가"에 답을 받고 나니 `resizeGroup` 본문은 한 줄도 고칠 것이 없었다.
- 골든 150개 중 셋이 깨졌고, 새 기대값을 실제 실행 결과로 다시 기록하면서 골든 `meta.intentionalChanges` 에 무엇을 왜 바꿨는지를 남겼다. 골든에 "의도적으로 바꾼 기대값"을 기록하는 자리가 이때 생겼다.
- 단위 테스트가 38개에서 45개가 됐다. 새 7개는 시나리오 결과가 아니라 그 결과를 낳는 성질(네 조작의 정책이 같은가, 한 칸만 겹쳐도 상대의 다른 행 조각이 사는가)을 단언한다.

### 1. 연습 버전 (다음 작업)

같은 안무의 여러 판본과, 연습할 때마다 남기는 기록을 저장한다.

- 안무 버전과 연습 기록은 **다른 축**이다. 안무가 바뀌면 새 버전, 같은 안무를 또 연습하면 새 기록이다.
- "얼마나 나아졌는지"는 자동으로 계산되는 것(버전 사이의 안무 차이)과 사람이 남기는 것(속도, 성공 여부, 메모)으로 나뉜다.
- 저장 위치를 먼저 정해야 한다. 지금 최근 프로젝트 10개가 payload 통째로 localStorage에 들어가 있어 용량이 이미 빠듯하다([버그 기록](BUG_REPORTS.md)의 "아직 남아 있는 위험" 참조).

**대기 조건**: 아래 미결정 사항의 "버전마다 다른 영상을 쓰는가"가 정해져야 저장 포맷을 확정할 수 있다.

### 2. 영상을 잘라 내보내기 (옛 "시퀀스 엔진 이식")

안무표에서 고른 구간을 영상 파일로 잘라 낸다. 원래 "서버가 필요해질 수 있는 유일한 자리"였는데, 2026-09-09 에 영상 보관을 위해 `server.py`(표준 라이브러리만)가 먼저 생겼다. 자르기를 붙인다면 그 서버에 ffmpeg 호출을 얹는 것이 자연스럽다 — 다만 그 순간부터 ffmpeg 설치가 전제가 된다.

**2026-09-10 에 절반이 됐다.** 영상 패널의 `구간 자르기` 가 In/Out 으로 잡은 구간을 `POST /api/clips/trim` 으로 보내면 서버가 ffmpeg 으로 다시 인코딩한 MP4 를 보관 폴더에 만들고 앱이 그 파일로 갈아 끼운다(템포·마커의 시각도 함께 당긴다). ffmpeg 은 **선택 의존성**으로 두었다 — 없으면 이 버튼만 꺼진다(`/api/health` 의 `ffmpeg`). 그리고 영상 구간 ↔ 안무표 구간 **마커**(`media.markers`, `domain/markers.js`)가 생겨 "이 영상 토막이 이 마디"를 기록하고 박자에 반영할 수 있다. 남은 절반은 반대 방향 — **안무표에서 고른 구간**(마디·블록)을 템포로 초 구간으로 바꿔 잘라 내보내는 것 — 인데, 마커의 카운트 구간과 `domain/tempo.placementToSpan` 이 이미 그 재료다.

원래 이 항목은 "영상 시퀀스를 편집하는 엔진을 다른 프로젝트에서 통째로 들고 온다"였다. 2026-09-09에 그 프로젝트(`LLM-Movie-Maker`)를 실제로 열어 보고 전제가 틀렸음을 확인했으므로, 조사 결과를 남겨 다음에 이 결정을 다시 할 때 처음부터 뒤지지 않게 한다.

#### 확인한 사실

`LLM-Movie-Maker`는 **Python + FastAPI 서버**다(`.py` 94개). 영상 처리의 실체는 `ffmpeg`을 자식 프로세스로 띄우는 코드이고, 하는 일도 다르다 — 프롬프트로 클립을 만들어 마지막 프레임으로 체이닝해 붙이는 **생성** 도구다. 브라우저에는 프로세스도 파일시스템도 없으므로 **그대로 옮겨 심을 수 없다.**

다만 서버를 두기로 한다면 재사용성은 좋다.

| 가져올 것 | 재사용성 | 근거 |
|---|---|---|
| `app/media.py` (297줄) | **그대로** | 프로젝트 import가 0개다. `asyncio`·`subprocess`·`pathlib`뿐이라 job·clip·DB 개념을 모른다 |
| `ports.py`의 `Media`/`AsyncMedia` | **그대로** | 이미 포트 뒤에 있다. 이 앱의 `SequenceEnginePort`와 같은 모양 |
| `domain/timing.py` | 개념만 | `TimeGrid`·`Snap` — "고른 값과 실제로 만들어질 값을 함께 든다". [포트 계약](PORTS.md)의 `Tempo`가 같은 문제를 안고 있다 |
| `app/video.py` | 안 됨 | 외부 생성 모델 서버 호출. 안무와 무관 |
| `app/pipeline.py` | 안 됨 | 클립 생성 잡 오케스트레이션 |

두 가지를 함께 적어 둔다. **첫째, 정작 필요한 자르기 함수가 없다** — 있는 것은 `extract_frame_at`·`concat_clips`·`mux_tracks`·`encode_clips`로 전부 만들어 붙이는 쪽이고 `trim`/`subclip`은 없다. 다만 `-accurate_seek -ss` 패턴이 이미 있어 함수 하나를 같은 자리에 더하는 정도다. **둘째, 값의 대부분이 코드가 아니라 주석에 박힌 하드윈 지식이다** — "끝을 넘겨 찍으면 ffmpeg은 빈 파일을 남기는 게 아니라 오류로 죽는다" 같은 것들이 297줄보다 값지다.

#### 그래서 무엇을 하나

**"재사용할 수 있다"가 "서버로 바꿀 이유"는 아니다.** 가져올 수 있는 것은 ffmpeg 래퍼 297줄인데 서버를 도입하며 치르는 값이 훨씬 크다 — 클론해서 정적 서버 하나면 끝나던 것이 Python 환경 + ffmpeg 설치 + 프로세스 관리가 되고, `tools/check-arch.mjs`가 지키는 계층 규칙 바깥에 두 번째 런타임이 생긴다.

순서를 이렇게 잡는다.

1. ~~**영상 패널을 먼저 만든다.**~~ 2026-09-09 에 됐다(위 `구현 완료`). 서버 없이 됐고, 이제 그다음 무엇이 아쉬운지를 실제로 써 보고 판단할 수 있다.
2. 아쉬운 것이 **구간 반복·속도 조절**이면 브라우저만으로 된다(`playbackRate`, `currentTime` 루프). 서버 불필요.
3. 아쉬운 것이 **잘라서 파일로 내보내기**면 그때 비로소 갈림길이다 — `WebCodecs`로 브라우저에서 갈지, `media.py`를 가져와 서버로 갈지.

**대기 조건**: 3단계에 실제로 도달할 것. 지금은 아직 없는 문제다.

### 3. 영상에서 관절 가동 범위 재기 (계산부는 있고 모델이 없다)

영상 속 사람의 관절 각도를 재서 동작마다 **가동 범위**(가장 많이 굽힌 각 ~ 가장 많이 편 각)를 남긴다. 목적은
자세 교정이 아니라 **기록**이다 — 같은 동작의 지난 테이크와 오늘 테이크를 견줘 "무릎이 20° 더 열렸다" 를
말할 수 있으면, 위 1번의 연습 기록이 사람이 적는 별점 말고 잰 값 하나를 더 갖게 된다.

**2026-09-11 기준으로 계산·모델·추정기까지 서 있고, 안무표에 붙는 화면만 없다.**

| 파일 | 하는 일 |
|---|---|
| `src/ports/pose.js` | 자세 추정기 계약. 배치 분석(`analyze`)이고 던지지 않는다. **모델의 점 인덱스를 경계 밖으로 내보내지 않는다** — 어댑터가 `leftElbow` 같은 이름으로 옮겨 넣으므로 모델을 갈아 끼워도 아래 계산이 안 바뀐다 |
| `src/domain/pose.js` | 점 → 관절 각도 10개 + 상체 기울기. 각도는 **관절 안쪽 각(180° = 곧게 편 상태)** 으로 규약을 한 번만 정한다 |
| `src/domain/poseTracks.js` | 누가 누구인지 잇는다. 한 사람이면 자동, 여럿이면 앵커를 찍고, 스쳐 지나 헷갈린 구간은 `ambiguous` 로 드러낸다 |
| `src/domain/rom.js` | 구간·카운트별 가동 범위 요약, 좌우 대칭, 테이크 사이 비교. 못 본 프레임을 분모에 남겨 `coverage` 로 알린다 |

| `server.py` + `src/adapters/modelServer.js` | 모델을 어디에 받아 둘지(`⚙ 설정` 의 `자세 분석 모델`)와 받기 |
| `src/adapters/pose/mediapipePose.js` | 받아 둔 파일로 `PoseEstimator` 계약을 채운다. `<video>` 를 탐색하거나 이미 뽑아 둔 프레임을 받는다 |
| `tests/pose-check.html` + `tools/make-pose-clip.py` | 관절 위치를 미리 정해서 그린 합성 영상으로 분석이 맞는지 보는 검사 페이지. world 좌표를 돌려 보는 **3D 보기**도 여기 있다 |

**2026-09-11 에 실물로 확인한 것.**

- 정답을 아는 합성 영상에서 **넣은 가동 범위와 잰 가동 범위가 소수점까지 같다**(왼 팔꿈치 110.0°, 왼 무릎 55.0°,
  오른쪽 둘은 0.0°). 한 사람짜리라 앵커 없이 궤적이 저절로 섰다.
- 실제 사람 사진에서는 관절 15개가 신뢰도 0.96 이상으로 잡히고 미터 좌표(world)로 들어온다.
- **합성 뼈대는 MediaPipe 가 사람으로 보지 않는다**(0명). 실제 사람으로 학습된 모델이라 선 그림에는 아무도 없다고
  답한다 — 그래서 합성 영상은 "우리 계산이 맞는가" 만 보고, "모델이 도는가" 는 실제 사진으로 따로 본다.
- 속도는 480x640 기준 초당 50장 안팎이었다(full 모델, 브라우저).

**⚠ 이 검사가 잡은 결함 — 정규 좌표는 각도를 일그러뜨린다.** 화면 좌표는 가로를 폭으로 세로를 높이로 나눈 값이라
480x640 영상에서 가로가 0.75배로 눌려 있다. 그 좌표로 각을 재면 넣은 110.0° 가 **93.9°** 로 나왔다. 프레임마다
`aspect`(폭/높이)를 좌표와 함께 실어 보내고 각을 잴 때 되돌리는 것으로 고쳤다(`ports/pose.js` 경계 ②-a,
`domain/pose.spaceOf`). world 좌표에는 해당하지 않는다 — 이미 미터라서 눌린 축이 없다. 되돌린 좌표는 각도
계산에만 쓰고 오버레이·클릭 판정은 원래 좌표를 그대로 쓴다(안 그러면 화면 위치와 어긋난다).

**⚠ y 축 규약은 재야 한다(2026-09-12).** MediaPipe 는 화면 좌표도 world 좌표도 y 가 **아래로** 자란다
(실측: 코 -0.578, 발목 +0.447). 캔버스도 아래로 자라므로 그대로 그리면 맞는데, 처음에 뒤집도록 두어 사람이
물구나무로 그려졌다. 단위 테스트가 "코가 발목보다 위에 그려진다" 를 못박고 있다.

**⚠ 3D 는 정면만 믿을 수 있다(2026-09-12).** world 좌표를 세로축 둘레로 돌려 보면 0° 에서는 영상의 자세와 맞지만,
75° 쯤 돌리면 앞뒤로 벌린 다리가 거의 겹쳐 보인다 — 카메라 한 대에서 뽑은 깊이라 정보가 얇기 때문이다
(실제 사진에서 깊이 폭이 0.244m 에 그쳤다). "몸이 어느 쪽을 보는가" 정도는 읽히지만 옆모습의 각도는 못 믿는다.
각도·가동 범위를 world 로 재는 것은 그대로 유효하다 — 그건 관절 사이의 상대 위치라 절대 깊이만큼 민감하지 않다.

**메시는 2026-09-12 에 만들었다 — 다만 "평균 몸을 관절에 맞춰 늘린 것" 이다.** `domain/bodyMesh.js` 가 뼈마다 통을
씌우고 몸통을 어깨선~허리~엉덩이선으로 잇고 머리를 얹어 꼭짓점 232개·면 124개짜리 몸을 만들고,
`ui/meshView.js` 가 먼 면부터 칠해 가림을 푼다. 의존성은 하나도 늘지 않았다. 영상 위에 겹치기(화면 좌표)와
따로 떼어 돌려 보기(world 좌표)가 둘 다 된다.

⚠ **이것은 SMPL 같은 몸매 복원이 아니다.** 자세는 맞지만 몸집은 `RADII` 표의 평균값이라 그 사람의 체형·옷이
반영되지 않고 실루엣에 딱 달라붙지 않는다. 진짜 메시를 얻으려면 HMR 계열 모델(PyTorch·GPU)을 서버에 올려야 해서
"표준 라이브러리만" 이 깨진다 — 그 선택지는 남겨 두되 지금은 닫아 두었다. MediaPipe 는 점 33개만 내주고 GHUM
메시는 학습에만 쓰여 밖으로 나오지 않는다.

**2026-09-12 에 앱에 붙었다.** 영상 패널의 `자세 분석` 구획(`ui/poseView.js`)에서 돌리고, 영상 위 오버레이
(`ui/poseOverlay.js`, 채널 B)가 관절·메시를 겹쳐 그리며, 영상 위를 눌러 인물을 고른다. 상태는
`usecases/poseCommands.js` 가 `session.pose` 에 요약만 둔다 — 관절점은 `app/main.js` 의 모듈 변수다.

**남은 것은 하나다.** 결과를 어디에 남길지 — 마커·테이크(위 1번)와 붙는다. 지금 분석 결과는 **저장되지 않고**
영상을 바꾸면 사라진다. 원본 landmark 는 프로젝트 파일에 넣기에 너무 크므로 클립 옆 사이드카 파일로 두고,
요약(카운트별 각도·가동 범위)만 프로젝트에 싣는 쪽이 자연스럽다. 그것이 붙으면 위 1번의 "이 동작이 지난주보다
20도 더 열렸다" 가 완성된다.

⚠ 분석은 **영상 파일에만** 된다. 유튜브는 iframe 안에서 재생되어 픽셀을 읽을 수 없다 — 잘라내기와 같은 조건이다.

### 4. 안무 작성을 더 쉽게

**2026-09-12 에 구체화했다.** 이 도구로 안무표를 채우는 길 스무 가지를 전부 적고, 그중 무엇이 막혀 있는지와 어떻게 열지를 [편집 흐름](EDITING_FLOWS.md)에 따로 두었다. 요지는 하나다 — 영상을 보며 적을 때 **사람은 이름을 맨 나중에 붙이는데 도구는 맨 처음에 요구한다.** 블록을 놓는 유일한 길이 동작 목록의 항목을 가리키기 때문이다.

막힌 곳은 다섯이었다. ① 재생 위치에서 바로 블록을 놓을 수 없다 ② 이름 없이 자리를 잡을 수 없다 ③ 마커가 블록이 되지 않는다 ④ 마디 위의 묶음(파트)이 없다 ⑤ 잰 가동 범위가 화면에 안 나온다. **①②③ 은 2026-09-12 에 열렸다**(받아 적기 — 영상 패널의 `③` 단계와 단축키 `B`).

네 단계로 연다. ①받아 적기 → ②나중에 이름 붙이기 → ③파트 → ④기록과 비교.

**1단계는 끝났다(2026-09-12).** 막혀 있던 시나리오 셋(강습 영상 받아 적기, 공연에서 대목 뽑기, 내 촬영본 받아 적기)이 열렸다. 다음은 **2단계 — 나중에 이름 붙이기**다: 이름 없는 블록만 모아 한 화면에서 채우고, 되풀이되는 것을 "아까 그것"으로 묶고, 그때 동작 목록·카테고리에 등록한다. 지금은 고른 블록에 한 번에 한 이름을 붙이는 것까지만 된다.

아래는 그와 별개로 확인된 자잘한 마찰이다.

- 동작을 한 번 옮길 때마다 보드 전체를 다시 그린다.
- 루틴 색을 고를 수 없다. 여덟 색이 만든 순서대로 자동 배정되고 그 순번이 저장되지도 않아, 파일을 다시 열면 다른 루틴이 같은 색을 쓸 수 있다.
- `전체 초기화(링크 포함)` 이나 `전체 불러오기` 뒤에 선택 표시가 남아 `루틴으로 편성 (N)` 버튼이 계속 떠 있다. 눌러도 가리키는 배치가 없어 아무 일도 일어나지 않는다.
- 메인 `Undo` 직후에 무엇이든 하면 되돌리기 단계가 하나 더 쌓이고 다시 실행 대기열이 날아간다. 원인은 카테고리 정규화의 정렬이라 고치면 저장 파일의 키 순서가 달라진다.

링크 되돌리기와 리사이즈의 충돌 규칙은 여기서 빠졌다 — 둘 다 2026-09-07 에 닫혔고 위 `구현 완료` 에 있다. 대신 그 자리에 하나가 들어왔다: 복사만 층 재정렬을 부르지 않는 것이 이제 네 조작 중 유일한 예외가 되어 [다음에 고칠 후보](deviations.md#다음에-고칠-후보) 의 1번이다. 나머지 마찰의 전체 목록과 고칠 때 함께 해야 할 일은 [일부러 두고 온 것](deviations.md)에 있다.

## 미결정 사항

시작하기 전에 답이 필요한 것들이다.

- ~~**intro 행(row 0)을 시간 축에 넣는가.**~~ **넣기로 했다(2026-09-09).** 좌표식이 intro 를 음수 카운트로 분기 없이 처리하고, 재생 헤드도 거기 그대로 선다.
- ~~**자세 모델을 어디에 두는가.**~~ **2026-09-11 에 정했다: 브라우저가 계산하고, 파일은 사용자가 설정에서
  정한 폴더에 받아 둔다.** `@mediapipe/tasks-vision@1.0.1` 의 `vision_bundle.mjs` 는 진짜 ES 모듈이라 번들러도
  npm 도 없이 브라우저가 그대로 읽고, `server.py` 는 파일을 받아 두고 `/models/<이름>` 으로 내주기만 한다 —
  **파이썬 패키지가 하나도 늘지 않는다.** 없으면 `/api/health` 의 `pose:false` 로 알리고 그 기능만 꺼지는
  ffmpeg 과 같은 모양이다. 기본 위치는 저장소의 `models/`(gitignore)이고 `⚙ 설정` 이나 `--models` 로 바꾼다.
  받는 양은 크기에 따라 17.2MB(lite) · 20.6MB(full) · 41.9MB(heavy)다. 버전은 못 박았다 — 모델이 조용히
  바뀌면 어제 잰 각도와 오늘 잰 각도를 나란히 놓을 수 없다.
- **버전마다 영상이 다른가.** 같은 안무를 여러 번 촬영한 영상을 버전마다 붙인다면 영상 정보가 버전 안으로 들어가야 한다. 지금은 **프로젝트 공통**으로 두었다(`media` 블록이 파일 최상위에 있다). 나눌 때 옮기기 쉽도록 `tempo` 와 `source` 를 블록 하나로 묶어 두었다.
- **루틴 편집 보드에도 카운트 ↔ 시간을 적용하는가.** 루틴은 자체 격자라 별도 템포가 필요할 수 있고, "루틴은 시간 매핑 없음"으로 못 박는 편이 단순하다.
- ~~**로컬 영상 파일을 어디까지 지원하는가.**~~ 2026-09-09 에 두 단으로 정했다. 기본은 **파일명만** 남기고(`{kind:'file', name}`) 다시 열면 같은 파일을 다시 고르라고 안내한다. 설정에서 보관 폴더를 지정하면 File System Access API 로 그 폴더에 복사하고 상대 경로(`path`)까지 남긴다 — 핸들은 IndexedDB 에 두고, 크롬 계열에서만 된다.
- **엔진 상태를 프로젝트 파일에 넣는가.** 넣으면 프로젝트 JSON이 커지고 localStorage 용량을 때린다. 크기 상한을 두고 초과 시 어떻게 할지 정해야 한다.

## 하지 않기로 한 것

- **클라우드 저장.** 2026-03-19에 Dropbox 연동을 붙였다가 하루 만에 397줄을 전부 걷어냈다. 단일 정적 HTML에 OAuth를 얹는 비용이 얻는 것보다 컸다. 다시 하려면 배포 형태부터 정해야 한다.
- **빌드 도구·번들러·npm/pip 의존성.** 브라우저가 그대로 읽는 ES 모듈로 유지하고, 2026-09-09 에 생긴 로컬 서버 `server.py` 도 파이썬 표준 라이브러리로만 쓴다. 대신 `file://` 더블클릭은 포기했다 — [튜토리얼](TUTORIAL.md)의 실행 방법을 따른다.
- **프레임워크 도입.** 상태 전파는 저장소 하나와 갱신 기술자 하나로 충분하다는 것이 이번 재구성의 결론이다.
