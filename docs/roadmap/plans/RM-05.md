# RM-05 check-principles — 기계로 잡히는 원칙을 검사기로

## 풀어 본 설명 — 2026-09-29

사람이 리뷰할 때마다 기억해야 했던 개발 원칙 가운데, 코드 글자만 보고도 어긴 것을 알 수 있는 다섯 가지(U-11 · U-12 · D-5 · R-6 · D-14)를 검사 스크립트 하나로 옮긴다. 원칙이 30개를 넘자 사람이 다 기억하지 못했다. 특히 「display 를 준 클래스가 hidden 숨김을 이긴다」(U-12)는 이미 적어 둔 원칙인데도 새 화면을 만들 때마다 다시 빠뜨려 네 번 났다.

### 무엇

앱 화면은 바뀌지 않는다. 개발자가 돌리는 검사가 하나 는다. 지금 있는 두 검사(계층 방향, 문서 등록)와 같은 꼴로 `tools/` 에 검사기를 하나 두고, 한 번 돌리면 다섯 원칙을 차례로 훑는다. 어긴 자리를 「파일:줄 — 어느 원칙 — 어떻게 고치나」로 찍고, 하나라도 있으면 실패로 끝난다. 훑는 것은 다섯이다. ① U-11: 속성을 빈 문자열로 끄는 자리(`dataset.x = ''`). ② U-12: CSS 에서 display 를 켜는 선택자에 짝이 되는 `[hidden]` 규칙이 없는 자리. `index.html` 의 스타일과 뷰가 문자열로 들고 있는 스타일을 모두 본다. ③ D-5: `Number(x) || 기본값` 처럼 0 을 기본값으로 덮어 버리는 자리. ④ R-6: 마크업이 이미 클래스를 준 요소에 `className =` 로 통째 대입하는 자리. ⑤ D-14: 이름으로 잇는 표끼리 맞춰 세기. 단축키 표의 커맨드 이름이 실제 커맨드 목록에 있는지를 부팅 경고가 아니라 검사에서 잡는다.

### 왜

원칙 문서는 실제로 겪은 버그에서 뽑은 것이다. 그런데 「어떻게 확인할까」가 grep 한 줄로 되는 것까지 사람이 리뷰 때마다 떠올려야 했다. 떠올리지 못하면 같은 버그가 되풀이된다. U-12 가 그 증거다. 영상 프레임, 자세 분석 줄, 접는 단계, 설정 화면에서 같은 원인으로 네 번 났다. 버그 기록의 「화면에 남거나, 없는 것이 보인다」 부류 가운데 아홉 번째 버그도 여섯 번째와 원인이 똑같았다. 규칙을 몰라서가 아니라 새 컴포넌트마다 다시 빠뜨려서 생긴다. 게다가 이런 버그는 증상이 조용하다. 숨긴 버튼이 보이거나, 저장했다 열면 0행이 1행으로 밀리거나, 글쇠 하나가 말없이 죽는다. 그래서 화면만 봐서는 원인이 드러나지 않는다. 전역 규칙도 「잴 수 있으면 기계가 잰다」고 한다.

### 어떻게

- `tools/check-arch.mjs` · `tools/check-docs.mjs` 와 같은 꼴로 짠다. 의존성 0, 노드 표준 모듈만 쓰고, 어긴 것이 있으면 종료 코드 1로 끝낸다.
- 원칙마다 규칙 하나: { 원칙 번호, 훑을 파일, 찾을 꼴, 고치는 법 }을 표 한 줄로 둔다. 원칙이 늘면 줄만 더한다.
- U-11 · D-5 는 정규식 한 줄이면 된다. D-5 는 지금 src 에 19자리가 걸리는데, 0 이 뜻을 갖는 자리(행 · 인덱스 · 카운트)인지는 사람이 가려야 한다. 그래서 괜찮은 자리는 그 줄에 표식 주석을 달아 통과시킨다.
- R-6 은 `className =` 대입이 걸리는 자리가 많다(대부분 새로 만든 요소라 괜찮다). 그래서 `index.html` 마크업에서 id 와 원래 클래스를 뽑고, 대입 대상이 그 id 로 잡은 요소이면서 원래 클래스가 둘 이상일 때만 잡는다.
- U-12 는 CSS 를 모은다. `index.html` 의 style, 그리고 뷰 파일에서 백틱 문자열로 들고 있는 스타일이다. 거기서 display 가 none 이 아닌 선택자를 뽑고, 같은 선택자의 `[hidden]` 짝(또는 전역 규칙)이 있는지 본다.
- D-14 는 단축키 표와 커맨드 이름을 정적으로 대조한다. 필드 쪽은 RM-01 의 필드 등록표가 이미 불러오는 순간 던지므로 다시 하지 않는다.
- 지금 코드에서 먼저 한 번 돌려 이미 있는 위반을 어떻게 다룰지 정한다(갈림 1). 그다음 CLAUDE.md 의 「고치기 전에 돌리는 것」 목록에 다섯 번째 명령으로 올린다.
- 원칙 문서의 다섯 항목 「어떻게 확인할까」에 「이 검사기가 잡는다」는 줄을 더한다. 검사기에는 일부러 틀린 조각을 넣으면 붉어지는지 보는 자기 시험을 둔다.

### 갈리는 대목

- 이미 코드에 있는 위반을 어떻게 다루나
  - 이번에 전부 고치고 0에서 시작 — 검사가 깨끗하게 선다. 다만 D-5 의 19자리를 하나씩 가려 고치면 동작이 바뀔 수 있어, 골든을 건드리는 동작 변경 커밋이 따로 붙는다. 크기가 S 를 넘을 수 있다.
  - 지금 위반을 기준선 목록으로 얼리고 새것만 잡는다 — S 안에 끝나고 동작은 바뀌지 않는다. 대신 목록이 줄어들지 않고 쌓일 수 있으니, 목록 개수가 늘면 실패하게 해 둔다.
  - 자리마다 괜찮다는 표식 주석을 단다 — 그 줄에서 왜 괜찮은지 읽힌다. 다만 처음에 주석 수십 개가 코드에 들어간다.
- U-12 를 검사로 잡나, 전역 규칙 한 줄로 없애나
  - 검사: display 선택자마다 [hidden] 짝이 있는지 센다 — 지금 방식(짝을 손으로 적기)을 그대로 두고 빠뜨림만 잡는다. CSS 를 문자열에서 뽑아야 해서 검사기가 가장 복잡한 부분이 된다.
  - 전역 [hidden]{display:none !important} 한 줄을 두고 검사는 그 줄이 있는지만 본다 — 원인 자체가 사라져 짝 22개가 필요 없어진다. 다만 hidden 을 붙인 채로 일부러 보이게 하던 자리가 있으면 동작이 바뀐다. 동작 변경 커밋으로 따로 내고 화면에서 확인해야 한다. RM-17(디자인 토큰)과 CSS 자리가 겹친다.
- 언제 돌게 하나
  - CLAUDE.md 목록에만 올린다(지금 두 검사와 같다) — 도구가 늘지 않는다. 대신 돌리는 것을 잊으면 그만이다.
  - 커밋 훅에 넣는다 — 전역 규칙(「빠른 검사는 커밋 훅」)과 맞고 몇 초 안에 끝난다. 다만 저장소에 훅 자리(`.githooks/` + core.hooksPath)가 아직 없어 새로 세워야 한다. 그러면 check-arch · check-docs 도 함께 올리는 것이 자연스럽다.

### 조심할 것

- 판의 「아홉 번 재발」은 과장이다. 버그 기록에서 U-12 원인은 네 번 났다. 「아홉」은 그 부류의 아홉 번째 버그라는 뜻이다. 로드맵 문구를 고칠 때 바로잡는다.
- R-6 · D-5 는 글자만 봐서는 옳고 그름이 갈리지 않는다(새로 만든 요소, 0 이 뜻 없는 자리). 너무 넓게 잡으면 경보가 잦아지고, 결국 사람이 검사를 무시하게 된다. 오탐을 줄이는 쪽으로 좁힌다.
- U-12 는 CSS 가 `index.html` 과 뷰 파일의 백틱 문자열 두 곳에 흩어져 있다. 문자열에서 CSS 를 뽑다 보면 R-7(주석 속 백틱)과 같은 파싱 함정을 밟을 수 있다.
- 위반을 고치는 일과 검사기를 더하는 일을 한 커밋에 섞지 않는다. 고침이 동작을 바꾸면(D-5, 전역 [hidden]) 골든과 함께 동작 변경 커밋으로 따로 낸다.
- D-14 대조는 RM-09(명령 등록부 — 라벨 · 단축키 · 실행의 주인 하나)가 들어오면 표가 하나로 합쳐져 필요 없어진다. 지금은 가볍게 두고, RM-09 때 걷어낸다.
- RM-06(문서의 라벨 인용 대조)도 `tools/` 의 같은 꼴 검사기다. 공통 뼈대(파일 훑기 · 보고 꼴)를 여기서 만들어 두면 RM-06 이 가벼워진다.

### 판의 옛 설명

> grep 으로 잡히는 개발 원칙(U-11 · U-12 · D-5 · R-6 · D-14)을 검사기 하나로 옮긴다. U-12 는 같은 원인으로 아홉 번 재발했다.
