# RM-52 server.py 연결 대기열 5 — 모듈 몰림에 연결이 끊겨 앱이 반쯤 뜸

server.py 는 ThreadingHTTPServer 를 기본 대기열 5 로 연다. 그래서 캐시 없이 처음 열 때 ES 모듈 요청 수십 개가 한꺼번에 오면 연결의 절반쯤이 끊기고 앱이 반쯤만 뜬다. 대기열을 128 로 늘린 서버 갈래를 하나 두어 그 몰림을 받아 내고, 같은 몰림을 실제 서버에 걸어 끊김이 0 인지 재는 회귀 시험을 둔다. 판의 다른 항목과 겹치지 않는다.

크기 S · 2026-11-03 에 판에서 다시 다듬었다

## 다시 다듬기 전의 설명

> ThreadingHTTPServer 의 request_queue_size 가 기본값 5 라, 캐시 없는 첫 열기(새 프로필 · 폰 첫 방문 · 캐시 끔)에서 ES 모듈 수십 개가 몰리면 연결이 ERR_CONNECTION_RESET 으로 끊기고 앱이 판 없이 반쯤 뜬다. 잰 것: 시험용 크롬 캐시 끔 다시 불러오기 — 127.0.0.1 · 100.86.195.60 둘 다 여러 번 깨짐(한 번에 모듈 17~60여 개 실패). 파이썬으로 모듈 100개 동시 GET — 기본 서버 3/3 번 모두 약 절반(52·62·54 개) 끊김, 같은 서버에 request_queue_size=128 만 바꾸면 3/3 번 끊김 0(kern.ipc.somaxconn=128). 원인 재현 확인함 — 고칠 자리는 server.py 의 ThreadingHTTPServer 생성(1979 줄 근처)에서 대기열을 늘리는 것.

## 요구

- server.py 가 띄우는 서버의 연결 대기열(listen backlog)을 기본 5 가 아니라 128 로 연다 — 몰림을 받을 서버 갈래 하나에 값을 두고 main 이 그것을 쓴다
- 캐시 없는 첫 열기처럼 정적 모듈 100개를 한꺼번에 GET 해도 끊김(ECONNRESET) 없이 모두 200 으로 온다
- 대기열을 늘려도 지금 서버의 동작(정적 파일 · /api · --port 0 으로 고른 포트 찍기 · 종료)은 그대로다
- 겪은 버그와 교훈을 버그 기록과 원칙 문서에 적는다(증상 · 원인 · 수정 · 재발 방지)

## 조심할 것

- 동시 100 요청 시험은 기계 부하에 기댄다 — 커널 상한(macOS somaxconn 128)보다 많이 쏘면 다시 끊길 수 있으니 동시 수는 100 에 두고 128 을 넘기지 않는다. 흔들리면 그 조건(부하 · 동시 수)부터 재현으로 짚는다
- Node fetch(undici)의 기본 연결 풀이 한 주소에 연결을 몇 개까지 여는지에 따라 몰림이 실제로 안 생길 수 있다 — 고치기 전 코드에서 이 시험이 붉어지는지를 반드시 먼저 확인한다. 안 붉으면 Agent 의 connections 를 넉넉히 준다
- request_queue_size 는 서버를 열 때 listen() 에 한 번만 쓰인다 — 바깥에서 값을 덮어쓰는 꼴로 두면 생성 뒤에는 효과가 없으니 꼭 갈래의 값으로 둔다
- Tailscale 주소(100.86.195.60)로 띄운 두 번째 인스턴스도 같은 main 을 타니 함께 고쳐진다 — 이미 떠 있는 서버는 다시 켜야 반영된다
