# RM-50 블록 위 한글 바로 치기 — 첫 낱자가 떨어져 들어감

블록을 고른 채 한글을 바로 치면 첫 낱자가 조합 밖에서 맺혀 이름이 「ㅅㅡ윙」 · 「ㅎㅏㄴ」처럼 깨진다. 지금 코드에는 이미 「빈 입력을 열고 기본 동작을 막지 않는」 길(main.js 의 isImeKey)이 있지만, 실제 입력기에서는 그 길도 깨진다고 RM-51 이 쟀다. 그래서 이름 입력이 한글 낱자로 열렸을 때만, 입력이 맺힌 뒤 앞쪽의 흩어진 자모를 2벌식 규칙으로 다시 조합한다. RM-51 과 같은 결함이다(같은 자리 · 같은 까닭) — 이 항목에서 함께 고치고 RM-51 은 이 항목으로 닫는다.

크기 M · 2026-11-03 에 판에서 다시 다듬었다

## 다시 다듬기 전의 설명

> RM-15 마무리에서 실제 macOS 한글 2벌식 입력기로 확인: 블록을 고른 채(포커스는 body) 「스윙」(ㅅㅡㅇㅜㅣㅇ)을 바로 치면 이름 입력에 'ㅅㅡ윙' 이 들어간다(3번 중 3번, 「찰스턴」은 'ㅊㅏㄹ스턴'). 까닭: body 에서는 입력기가 조합하지 않아 첫 keydown 이 key='ㅅ' · keyCode 84 · isComposing=false 로 오고, bindHotkeys 의 글자 갈래가 그 낱자를 완성된 글자(initial)로 입력칸에 넣는다 — 그다음 모음은 이미 맺힌 ㅅ 과 합쳐지지 못하고 새 조합을 시작한다. Enter · F2 로 먼저 열고 치면 '스윙' 이 맞게 들어간다(Tab · Shift+Tab · Esc 도 조합 중에 맞게 동작 — 229 글쇠를 거른 뒤 keyCode 9 의 Tab 을 받는다). 고칠 길(추론): 글자 갈래에서 한글 낱자(ㄱ-ㅎ · ㅏ-ㅣ)면 initial 로 넣지 말고 빈 입력을 열어 포커스만 옮기거나, 첫 낱자를 넣은 뒤 다음 조합을 그 낱자와 합치는 길 — 어느 쪽이든 실제 입력기로 다시 확인해야 한다(만든 글쇠 이벤트 시험은 이 길을 못 잡는다).

## 요구

- 블록을 고른 채(포커스 body) 한글을 바로 치면 이름이 낱자로 깨지지 않고 「스윙」 · 「찰스턴」 · 「한」처럼 바르게 들어간다
- 흩어진 자모 줄(예: ㅅㅡ윙 · ㅊㅏㄹ스턴 · ㅎㅏㄴ)을 2벌식 규칙(겹모음 · 겹받침 · 받침 넘기기)으로 다시 조합하는 순수 함수를 둔다
- 다시 조합은 한글 낱자로 연 이름 입력에서만 하고, 조합 중(isComposing)에는 값을 건드리지 않는다 — Enter · F2 로 연 입력, 영문 첫 자로 연 입력은 지금과 같다
- 영문 · 숫자 · Shift 글자로 바로 치기, 받아 적기 글쇠 · S · ? 우선, 조합 중 Enter · Tab · Esc 의 지금 동작이 그대로다
- 실제 macOS 한글 2벌식 입력기로 「스윙」 · 「찰스턴」 · 「한」을 쳐서 바르게 들어가는지 확인하고, 그 결과를 기록에 남긴다

## 결정 사항

- 고칠 길 — 지금 코드의 「빈 입력 열기」 길이 실제 입력기에서 깨진다고 RM-51 이 쟀다. 그러면 첫 낱자를 어떻게 살릴까
  - 맺힌 뒤 자모를 다시 조합한다 — 바로 치기가 그대로 된다. 쟀던 세 경우(ㅅㅡ윙 · ㅊㅏㄹ스턴 · ㅎㅏㄴ)는 모두 다시 조합하면 바른 이름이 된다(추론함). 다만 조합이 끝난 뒤에 글자가 한 번 바뀌어 보이고, 2벌식 규칙의 순수 함수가 새로 생긴다
  - 한글 글쇠는 입력만 열고 첫 낱자를 버린다 — 막고(preventDefault) 빈 입력에 포커스만 준다. 결과가 늘 같지만, 사람이 첫 자를 다시 쳐야 한다 — 「바로 치기」가 반쯤만 된다
  - 한글은 Enter · F2 로만 연다 — 한글 낱자로는 열지 않고 「Enter 로 열어 치세요」를 알린다. 가장 단순하지만 RM-15 결정 Q49(한글도 바로 열린다)를 뒤집는다
  - **고른 답**: 맺힌 뒤 자모를 다시 조합한다
- RM-51 과 겹친다 — 같은 자리 · 같은 까닭의 결함이 판에 둘로 올라 있다
  - RM-50 에서 함께 고치고 RM-51 은 이 항목으로 닫는다 — 계획 · 브랜치 · PR 이 하나다. RM-51 이 잰 기록(ㅎㅏㄴ)은 이 항목의 시험 사례와 버그 기록으로 옮긴다
  - 둘을 따로 둔다 — 같은 함수를 두 PR 이 고쳐 충돌이 난다. RM-51 의 고칠 길 결정도 같은 물음이라 두 번 묻게 된다
  - **고른 답**: RM-50 에서 함께 고치고 RM-51 은 이 항목으로 닫는다

## 확인 시나리오

병합 뒤 눈으로 볼 사람 확인 줄이 생기면 브라우저 노드가 main 커밋의 임시 보드(예시 판 — 프로젝트 {pid}, 이 항목은 {item})에서 이 걸음을 따라 하며 영상을 찍는다(B667). 할 것: open(열기) · click(누르기) · type(적기) · wait(기다리기) · see(보임 확인).

| 걸음 | 할 것 | 대상 | 값 | 기대 |
|---|---|---|---|---|
| 1 | open | #/p/{pid}/{item} | — | 항목 카드가 열린다 |
| 2 | see | text=블록 위 한글 바로 치기 | 블록 위 한글 바로 치기 | 항목 이름이 보이고, 계획에 실제 입력기 확인 걸음이 적혀 있다 |

## 조심할 것

- 자모 다시 조합은 사람이 일부러 낱자를 치는 이름(예: ㅋㅋ)도 묶을 수 있다 — 한글 낱자로 연 입력에서만 켜고, 흩어진 자모끼리는 초성+중성 짝이 될 때만 묶는다
- 조합 중에 값을 바꾸면 입력기가 깨진다 — isComposing 인 input 에서는 절대로 값을 건드리지 않는다. compositionend 뒤에 input 이 안 오는 브라우저(Safari)도 있으니 끝낼 때 한 번 더 거친다
- 만든 글쇠 이벤트 시험은 실제 입력기의 길을 못 잡는다(RM-50 설명) — 자동 시험이 초록이어도 실기 확인 전에는 고쳤다고 하지 않는다
- main.js 의 isImeKey 주석이 지금 틀린 전제(막지 않으면 브라우저가 조합한다)를 적고 있다 — 고치지 않으면 다음 세션이 같은 길로 다시 간다
- src/domain 은 순수해야 한다 — hangul.js 는 문자 코드 셈만 쓰고, ui 가 domain 을 부르는 방향은 안쪽이라 check-arch 를 지난다
