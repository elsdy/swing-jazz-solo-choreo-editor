# RM-04 알림 세 급 — alert·prompt 를 토스트·인라인으로

## 풀어 본 설명 — 2026-09-29

앱이 사용자에게 무언가를 알리는 길을 세 급으로 나눈다. 작업을 멈춰야 하는 오류만 창을 띄워 막고, 알아야 할 실패는 화면 구석에 잠깐 떴다 사라지는 토스트로, 참고할 소식은 상태줄로 보낸다. 지금은 「병합 완료」 같은 성공 소식까지 브라우저 alert 창으로 뜬다. 그래서 영상을 틀어 놓고 동작을 받아 적는 도중에도 확인 버튼을 눌러야만 이어 갈 수 있다.

### 무엇

화면에서 달라지는 것은 셋이다. ① 알림 창(alert)이 거의 사라진다. 파일이 깨져 불러오기를 할 수 없을 때처럼 정말 막아야 하는 경우에만 앱 안의 모달이 뜬다. ② 「병합 완료: n개 그룹 배치됨」, 「카테고리는 최소 1개 이상 있어야 합니다」, 「동작 파일을 읽을 수 없습니다」 같은 문구는 화면 구석의 토스트로 뜨고 몇 초 뒤 저절로 사라진다. 누르지 않아도 작업이 이어진다. 무언가를 지운 뒤에는 「지웠습니다 · 되돌리기」 토스트가 떠서 그 자리에서 바로 되돌릴 수 있다. ③ 이름을 묻는 브라우저 prompt 창(동작 이름 변경, 카테고리 키 변경, 루틴 이름, 이 블록의 이름, 이 영상의 이름)은 그 칸 위에서 바로 적는 인라인 입력으로 바뀐다. 겉으로 보이지 않는 변화도 있다. 지금은 오류를 삼키고 아무 말도 하지 않는 자리(조용한 catch)가 27곳이다. 그 실패를 상태로 기록해 토스트나 상태줄로 사용자에게 닿게 한다.

### 왜

지금 실패가 사용자에게 닿는 길은 브라우저 alert 하나뿐이다. alert 는 모달이라 누르기 전까지 앱 전체가 멈춘다. 이 편집기의 핵심 흐름은 영상을 재생하면서 박자에 맞춰 블록을 받아 적는 것인데, 이 흐름을 모달이 끊는다. 성공 소식까지 모달이라, 알 필요만 있고 멈출 필요는 없는 말도 손을 멈추게 한다. 반대로 27곳의 조용한 catch 에서는 실패가 아예 보이지 않아 무엇이 안 됐는지 모른다. 너무 시끄러운 것과 너무 조용한 것을 한꺼번에 고치는 일이다. 뒤따르는 항목도 이 채널 위에 선다. RM-09(명령 등록부)는 명령 실행 결과를 이 채널로 알리고, RM-19(상태줄과 상시 안내 문장 걷기)는 이 항목이 정한 「참고 → 상태줄」 급을 채운다. 두 항목 모두 이 항목을 선행으로 둔다.

### 어떻게

- 유스케이스가 돌려주는 「무엇을 다시 그릴지」 묶음(Dirty)에는 지금도 notify 가 있지만 종류는 alert 하나만 받는다. 이것을 notice 채널로 정식화하고 급을 셋(막음 · 토스트 · 상태)으로 늘린다. 유스케이스는 계속 DOM 을 모르고 「이런 급의 이런 말」만 돌려준다.
- 렌더 라우터는 notice 를 지금처럼 맨 마지막에 적용한다. 「병합 완료」가 보드를 그린 뒤에 떠야 하는 순서는 그대로 지킨다.
- 화면 층에 토스트 뷰 하나(쌓기 · 몇 초 뒤 사라짐 · 「되돌리기」 같은 버튼 하나)와 앱 안 모달 하나를 새로 만든다. 조립부(main.js)가 둘을 주입한다. 이제 views.notify 가 곧바로 browserDialogs.alert 를 부르지 않는다.
- 유스케이스와 입력 층에 흩어진 dialogs.alert 호출(카테고리 · 동작 · 프로젝트 불러오기 · 파일 읽기 실패 등 10여 곳)을 notice 반환으로 옮긴다.
- dialogs.promptText 를 쓰는 다섯 자리(동작 이름 · 카테고리 키 · 루틴 이름 · 블록 이름 · 영상 이름)를 인라인 입력으로 바꾼다. Enter 는 확정, Esc 는 취소다. 취소하면 지금처럼 null 로 아무 일도 하지 않는다.
- 조용한 catch 27곳은 목록을 만든 뒤 급을 정해 하나씩 바꾼다. 사용자가 알아야 하는 실패만 토스트로 보내고, 나머지는 상태에만 남긴다.
- 지우기 유스케이스 뒤에 「되돌리기」 버튼이 달린 토스트를 띄운다. 버튼은 이미 있는 Undo 를 부를 뿐이다.
- 골든 어댑터는 notify 문구를 alertLog 로 모으고 있다. 문구와 순서를 그대로 두면 골든은 깨지지 않는다. 반대로 문구나 시점을 바꾸면 동작 변경 커밋으로 따로 내고 골든의 intentionalChanges 에 적는다.
- 구조를 옮기는 커밋(채널 정식화)과 동작을 바꾸는 커밋(alert→토스트, prompt→인라인)을 나눈다.

### 갈리는 대목

- 「참고 → 상태줄」 급을 어디에 보낼까 — 상태줄은 아직 없다(RM-19 가 세운다)
  - 이번에는 급만 정하고 토스트로 대신 띄운다 — RM-04 가 M 크기 안에 머문다. RM-19 가 상태줄을 세우면 그때 받는 자리만 바꾼다. 권장한다.
  - 최소한의 상태줄 한 칸을 여기서 같이 만든다 — 세 급이 처음부터 제자리를 갖는다. 대신 RM-19 의 몫(받는 중 · 저장됨 등을 한 자리에 모으기)과 겹쳐 크기가 커진다.
- 이름 입력의 인라인화를 이 항목에서 할까, RM-15(인라인 이름 편집과 Tab 으로 다음 ?)로 넘길까
  - prompt 창만 걷어 내는 최소 인라인을 RM-04 에서 한다 — 받아 적는 중에 모달이 뜨는 일이 이번에 끝난다. RM-15 는 그 위에 Tab 이동과 연속 이름 붙이기를 얹는다.
  - 이름 입력은 통째로 RM-15 에 넘기고, RM-04 는 alert·토스트만 한다 — RM-04 가 작아지고 겹치는 일이 없다. 대신 「이 블록의 이름」 prompt 는 RM-15 가 올 때까지 받아 적기 흐름을 끊는다.
- 토스트를 설정에서 끌 수 있게 할까(눈에 띄는 알림이라 사람마다 원하는 것이 갈린다)
  - 설정 없이 늘 켠다 — 막는 오류와 실패는 꺼지면 안 된다. 성공 소식만 짧게 떠서 거슬릴 일도 적다. 권장한다.
  - ⚙ 설정에 「성공 알림 토스트」 켬/끔(기본 켬)을 둔다 — 받아 적기에 방해된다고 느끼는 사람은 끌 수 있다. 실패 알림은 끄지 못하게 한다. 설정 필드가 하나 늘어난다.

### 조심할 것

- 골든은 alert 문구와 그 순서(보드 렌더 뒤 「병합 완료」)를 기록한다. 채널을 옮기는 커밋에서 문구나 시점이 바뀌면 골든이 깨진다. 구조 커밋과 동작 커밋을 나누고, 바꾼 기대값은 intentionalChanges 에 적는다.
- store 는 notify 의 kind 가 'alert' 가 아니면 던진다. 급을 늘릴 때 이 검사와 병합 규칙(나중 것이 이긴다)을 함께 고쳐야 한다. 토스트가 여러 개 겹칠 때 하나만 남는 것이 맞는지도 다시 본다.
- 계층 규칙을 지켜야 한다. 유스케이스는 토스트 뷰를 import 할 수 없고 급과 문구만 돌려준다. ui 와 input 도 서로 import 하지 않으므로, 입력 층의 파일 읽기 실패는 조립부를 거쳐 토스트에 닿게 배선한다.
- 인라인 입력은 제스처 · 단축키와 부딪칠 수 있다. 입력 중 Delete · 화살표가 보드 조작으로 새지 않도록 입력창 가드가 필요하고, 이것은 RM-13(키보드 편집)과도 닿는다.
- 「지웠습니다 · 되돌리기」는 기존 Undo 를 부르므로 RM-07(메인 Undo 직후의 유령 단계)의 결함이 그대로 드러날 수 있다. 되돌리기 한 번에 정말 지운 것이 돌아오는지 시험으로 확인한다.
- 토스트 · 인라인 입력은 화면에 보이는 문구와 조작 방법을 바꾼다. 기능 설명서 · 튜토리얼을 같은 PR 에서 고치고, 새 문구는 기존 어투를 따른다. 확인 방식은 confirm() 이 아니라 confirmOnce 로 둔다.

### 판의 옛 설명

> 막는 오류는 모달, 알아야 할 실패는 토스트, 참고는 상태줄로 나눈다. 지금은 성공 알림까지 alert 라 받아 적는 중에도 흐름이 끊긴다.
