# RM-66 창을 줄이면 영상 띠가 한 번 늦게 줄어든다

창을 줄이면 첫 resize 에서 영상 띠와 그 밑 조작 줄이 옛 폭(515px)으로 남고, resize 를 한 번 더 받아야 356px 로 맞는다. 원인은 이렇게 짚는다(추론함): videoPanel 의 resize 듣개가 placeBand 를 곧바로 부르는데, layout 의 resize 듣개(syncCellSize — 칸 크기 변수를 바꿔 띠 칸 폭을 움직인다)보다 먼저 돌면 바뀌기 전의 레이아웃을 잰다. 그래서 띠를 놓는 일을 모든 resize 듣개가 끝난 뒤로 미루어, 한 번의 resize 로 처음부터 그 크기로 연 것과 같은 값이 되게 한다. RM-63 과는 따로 가는 일이다 — 그 항목의 잼에서 찾았을 뿐, 그 코드를 부르지 않는다.

크기 S · 2026-11-03 에 판에서 다시 다듬었다

## 다시 다듬기 전의 설명

> 넓고 높은 창(1600x1500)에서 1200x820 으로 줄이면 첫 resize 뒤 영상 띠 조작 줄 폭이 515px 로 남고, resize 를 한 번 더 받아야 356px(처음부터 1200x820 으로 연 값)이 된다. 3번 중 3번 재현(iframe 뷰포트로 RM-63 실측 중). placeBand 가 줄이기 전의 레이아웃(띠의 padding-top 등)으로 재는 것으로 추론한다 — RM-63 의 고침과 무관하다(접힘은 그 폭에 맞게 고른다).

## 요구

- 고치기 전에 재현한다 — 1600x1500 에서 1200x820 으로 한 번 줄이면 조작 줄 폭이 515px 로 남는 것을 다시 재고, 두 resize 듣개의 등록 차례(main.js 가 initLayout 과 영상 패널을 붙이는 차례)가 그 까닭인지 확인한다
- 창 크기가 바뀌면 영상 띠는 다른 resize 듣개(칸 크기 맞춤)가 레이아웃을 바꾼 뒤에 잰다 — 한 번의 resize 로 처음부터 그 크기로 연 것과 같은 폭·자리가 된다
- 연달아 오는 resize 가 같은 틀(frame)에 여러 번 몰려도 띠는 한 틀에 한 번만 놓는다
- 띄운 창(float) 모드와 띠가 아닌 모드(지우기)의 resize 동작은 그대로다 — 기준점 캐시 버리기가 놓기보다 먼저 일어난다

## 순서

- 재현: iframe 뷰포트를 1600x1500 으로 열고 영상을 실어 띠를 세운 뒤 1200x820 으로 한 번 줄여 #thumbBar 폭을 잰다(세 번). main.js 에서 initLayout 과 영상 패널의 등록 차례를 읽고, 영상 듣개 안에서 syncCellSize 를 먼저 부르게 임시로 바꿔 보아 515→356 이 한 번에 맞는지로 원인을 확인한다 — 안 맞으면 다른 갈래(renderFlowSteps · 단계 칸 높이
- src/ui/resizeSettle.js 에 settleOnResize(win, { now, later }) 를 새로 둔다 — resize 마다 now() 를 곧바로 부르고, later() 는 requestAnimationFrame 한 번으로 미루며 이미 걸려 있으면 다시 걸지 않는다. 브라우저 전역은 인자로만 받는다(ui 계층, 어댑터 import 없음) · 복잡도 표지를 단다
- tests/unit/bandResize.test.mjs 에 요구 1~3 시험을 표지 [RM-66 요구 n] 과 함께 쓰고 고치기 전 붉음을 확인한다
- videoPanel 의 resize 듣개를 settleOnResize(window, { now: () => { floatOriginCache = null; }, later: syncDetached }) 로 바꾼다 — syncDetached 와 placeBand 의 몸은 그대로 둔다
- node --test tests/unit/bandResize.test.mjs 로 초록을 보고 node tools/check-arch.mjs 로 계층을 본다
- 같은 재현(1600x1500→1200x820 한 번)으로 #thumbBar 폭이 356px 인지, 1040px 을 넘나들 때 띠↔작은 창 바뀜이 그대로인지 다시 잰다
- docs/BUG_REPORTS.md 에 증상·원인·수정·재발 방지를 적고, 원칙(「resize 에서 재는 일은 모든 듣개가 레이아웃을 바꾼 뒤에」)이 새로우면 docs/PRINCIPLES.md 에 더한다

## 결정 사항

- 띠를 언제 다시 잴까 — resize 뒤 다음 틀인가, 띠 칸 크기 변화를 지켜보는가
  - resize 뒤 다음 틀(requestAnimationFrame)에 한 번 — 고치는 자리가 듣개 한 줄이고 몰린 resize 도 한 번으로 준다. 창 크기 말고 다른 까닭(단계 칸 접기 등)으로 띠 칸 폭이 바뀌는 것은 지금처럼 렌더가 맡는다
  - 띠 칸(.video-panel)에 ResizeObserver — 폭이 바뀌는 모든 까닭을 잡지만, placeBand 가 그 칸에 padding-top 을 쓰므로 되먹임이 없는지 따로 재야 하고 시험도 무거워진다
  - 듣개 등록 차례만 바꾼다(layout 을 먼저) — 가장 작지만 main.js 의 조립 차례에 기대는 숨은 약속이 되어, 차례가 다시 바뀌면 같은 결함이 돌아온다
  - **고른 답**: resize 뒤 다음 틀(requestAnimationFrame)에 한 번

## 조심할 것

- 원인은 추론이다 — 등록 차례 확인과 임시 바꾸기로 재현되지 않으면 고치지 않고, 단계 칸(bodyEl) 높이나 renderFlowSteps 갈래를 다시 잰다(재현 먼저 원칙)
- 띠 놓기가 한 틀 늦어지므로 그 사이 한 틀 동안 옛 자리가 보일 수 있다 — 지금도 두 번째 resize 까지 틀려 있으니 더 나쁘지는 않지만, 재생 헤드·오버레이가 같은 틀에 띠 자리를 읽는지(onSync) 함께 본다
- requestAnimationFrame 이 없는 시험 환경에서도 불러올 수 있게 win 을 주입받는다 — 모듈 머리에서 window 를 읽지 않는다
- 1040px 을 넘나드는 resize 에서 인라인 좌표 지우기(clearFloat)도 한 틀 늦어진다 — 폰 폭에서 오른쪽 위 작은 창이 한 틀 엉뚱한 자리에 서지 않는지 본다
