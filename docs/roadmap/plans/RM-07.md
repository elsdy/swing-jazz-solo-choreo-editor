# RM-07 메인 Undo 직후의 유령 단계

## 풀어 본 설명 — 2026-09-29

되돌리기(Undo)를 한 번 누른 직후에 무엇이든 하면, 되돌리기 단계가 하나 더 쌓이고 다시 실행(Redo)이 사라지는 결함을 고친다. 원인은 되돌릴 때 카테고리 순서가 가나다순으로 다시 정렬되는 데 있다. 편집기에서 삭제를 물어보지 않으므로 Undo 는 유일한 안전망이다. 그래서 Undo 는 한 번 누르면 정확히 한 단계만 되돌아가야 한다.

### 무엇

고치고 나면 Undo 뒤에 블록 하나를 놓아도 되돌리기 단계가 새로 쌓이지 않는다. 다시 실행도 Undo 로 막 되돌린 그 자리에서 이어진다. 지금은 Undo 뒤에 동작을 하나 하면 화면이 똑같은 단계가 하나 더 생긴다. 그래서 사용자는 한 동작을 넘어가려고 Undo 를 두 번 눌러야 하고, Redo 대기열은 통째로 날아간다. 부수 증상도 하나 있다. Undo 한 번에 동작 목록의 「카테고리별」 묶음 순서가 기본 순서(step·turn·jump·rotate·shimmy·fall)에서 가나다순으로 바뀐다. 이것도 함께 없앤다. 새 버튼이나 화면은 없다. 사용자에게 보이는 변화는 Undo·Redo 가 기대한 대로 움직이는 것뿐이다.

### 왜

편집기는 스냅샷 전체를 문자열로 바꿔 서로 견주고, 둘이 같으면 새 단계를 쌓지 않는다. 그런데 Undo 가 스냅샷을 되살릴 때 카테고리 정규화를 거치고, 이 정규화가 카테고리 키를 가나다순으로 정렬한다. 기본 카테고리는 가나다순이 아니다. 사용자가 새로 더한 카테고리도 끝에 붙기만 한다. 그래서 되살린 상태의 문자열은 원래 스냅샷과 글자 순서가 다르다. 다음 동작을 할 때 편집기는 이것을 새 상태로 판단해 단계를 하나 더 쌓고, Redo 는 버려진다. 링크를 되돌리기 범위에 넣는 일(deviations 의 undoable-links)을 하다가 이 결함이 드러났다. 그때는 그 일의 소관이 아니어서 고치지 않고, 오늘 동작을 그대로 못박는 특성화 시험만 심어 두었다. 이 항목이 그 빚을 갚는다(deviations.md 「다음에 고칠 후보」 3번).

### 어떻게

- 되살린 상태의 카테고리 키 순서가 스냅샷을 찍을 때와 같도록 만든다. 어느 쪽으로 맞출지는 forks 의 첫 갈림에서 정한다.
- 먼저 특성화 시험 「(보존) 카테고리 정렬 때문에 undo 직후 커밋이 유령 단계를 만든다」를 뒤집는다. 새 기대는 두 가지다. Undo 직후의 커밋은 단계를 쌓지 않는다. Redo 는 살아 있다.
- 바로 위의 「키 순서 안정성」 시험은 지금 카테고리를 미리 정렬해 결함을 피해 간다. 이 우회를 걷어내고, 정렬되지 않은 기본값에서 시작해도 통과하게 한다.
- 사용자가 카테고리를 더한 경우(끝에 붙는 키)와 옛 파일을 불러온 경우(불러올 때 이미 정렬됨)를 시험에 더한다. 두 경우 모두 Undo → 커밋 → Redo 가 한 단계씩 맞아야 한다.
- RM-01 의 필드 등록표가 되살리는 규칙을 필드마다 한 줄씩 들고 있다. 그래서 고칠 자리는 카테고리 줄 하나로 모인다. 파일 저장 규칙도 같은 표에 있어서, 저장 순서까지 바뀌는지를 한 자리에서 보고 판단한다.
- 저장 파일의 키 순서가 바뀌는 쪽을 고르면 마이그레이션을 함께 낸다. 옛 파일은 그대로 열려야 하고, 여러 번 저장해도 순서가 흔들리지 않아야 한다. 골든에 영향이 있으면 meta.intentionalChanges 에 무엇을 왜 바꿨는지 적는다.
- 이 일은 동작을 바꾸는 커밋이다. 구조를 옮기는 일과 섞지 않는다. deviations.md 의 비대칭 표에서 이 행을 내리고, BUG_REPORTS.md 에 증상·원인·수정·재발 방지를 적는다.

### 갈리는 대목

- 어느 쪽으로 순서를 맞출까 — 되살릴 때 정렬을 그만둘까, 언제나 정렬해 둘까
  - 되살릴 때는 정렬하지 않는다(스냅샷 순서 그대로) — 추천 — 파일에 저장되는 키 순서가 달라지지 않는다. 그래서 마이그레이션이 필요 없고 크기가 S 에 가깝다. 카테고리 순서는 사용자가 만든 순서로 남는다. 다만 파일을 불러올 때는 지금처럼 가나다로 정렬된다. 「불러오면 가나다, 편집 중에는 만든 순서」라는 불일치가 남는다.
  - 상태를 언제나 가나다순으로 둔다(처음 상태·카테고리 더하기도 정렬) — 판의 설명이 가정한 길이다. 되살려도 순서가 같아 유령 단계가 사라진다. 대신 새 안무의 기본 카테고리 순서와 동작 목록의 「카테고리별」 묶음 순서가 가나다로 바뀐다. 저장 파일의 키 순서도 달라지므로 마이그레이션과 골든 갱신이 따른다.
  - 중복 판정만 키 순서를 무시하게 한다 — 고칠 곳이 가장 적다. 유령 단계와 Redo 소실은 사라진다. 하지만 Undo 한 번에 카테고리 묶음 순서가 가나다로 바뀌는 눈에 보이는 흔들림은 남는다. 반쪽 고침이다.
- 카테고리 순서는 누구의 것인가 — 사용자가 정한 순서를 저장할까
  - 지금처럼 순서에 뜻을 두지 않는다 — 이번 항목은 Undo 결함만 고친다. 순서 규칙은 첫 갈림에서 고른 대로 굳는다.
  - 만든 순서를 사용자의 뜻으로 보고, 불러올 때도 정렬하지 않는다 — 불러오기·되살리기·저장이 모두 같은 순서를 지킨다. 대신 불러오기에서 정렬을 빼는 것은 또 하나의 동작 변경이다. 옛 파일을 열었을 때 묶음 순서가 달라질 수 있다. RM-34(루틴 색·순번 저장)처럼 「순서를 저장한다」는 일과 성격이 같으므로, 그 항목과 함께 정하는 편이 낫다.

### 조심할 것

- 골든 151개는 undo/redo 를 다루지 않는다. 골든이 다 통과해도 이 수정의 근거가 되지 못한다. 안전망은 단위 시험뿐이므로 Undo → 커밋 → Redo 를 한 단계씩 세는 시험을 반드시 심는다.
- 기본 카테고리의 키 순서가 곧 동작 목록 「카테고리별」 정렬의 묶음 순서다(defaults.js 의 경고). 정렬 성질을 건드리면 목록의 겉모습이 바뀐다. 기능 설명서나 튜토리얼 그림이 그 순서를 담고 있는지 확인한다.
- 저장 파일의 순서가 바뀌는 쪽을 고르면 같은 파일을 두 번 저장했을 때 바이트가 흔들리지 않는지 봐야 한다. 서버의 .history 안전망(RM-25)도 흔들리면 안 된다. 변화 없는 저장이 새 판본으로 쌓이면 안 되기 때문이다.
- 카테고리 순서는 서버 쪽 안무표 스키마에도 적혀 있다(PLAN_SCHEMA 는 두 번 적힌다). 파일 형식을 바꾸면 server.py 쪽도 대조한다.
- RM-04 의 「지웠습니다 · 되돌리기」 토스트가 이 Undo 를 그대로 부른다. RM-04 를 먼저 내면 사용자는 되돌리기를 누른 직후 유령 단계를 바로 겪는다. 그래서 순서상 이 항목을 RM-04 앞에 두거나 같은 무렵에 내는 편이 안전하다.
- 루틴 편집기의 되돌리기 스택은 따로 논다. 메인만 고치고 루틴 쪽의 순서 안정성도 같은 시험으로 한 번 확인한다.

### 판의 옛 설명

> Undo 한 번 뒤 무엇이든 하면 되돌리기 단계가 하나 더 쌓이고 다시 실행이 날아가는 결함을 고친다. 저장 파일의 키 순서가 바뀌므로 마이그레이션과 함께 낸다.
