## 겹치거나 여러 행에 걸친 동작이 어긋난다

같은 칸에 동작을 두 개 이상 놓으면 아래층으로 쌓이고, 8박자를 넘는 동작은 여러 행에 걸쳐 세그먼트로 쪼개진다. 이 두 구조를 다루다 생긴 버그가 **10건**으로 전체의 4분의 1에 가깝다. 반복의 실체는 코드가 아니라 규칙이었다 — "이동할 때 원래 층을 유지하는가, 가장 낮은 빈 층으로 내리는가"가 문서로 확정되지 않은 채 커밋 여덟 개에 걸쳐 왕복했다. 열 번째 항목이 그 값을 보여 준다. 다섯 달을 버틴 마지막 갈래("겹치면 지우는가 쌓는가")를 2026-09-07 에 **문서로 먼저 정하고** 나니 코드에서 바뀐 것은 정책 플래그 두 개뿐이었다. 아직 확정되지 않은 것은 층 정체성을 유지할 것인가 시각적으로 압축할 것인가 하나다.

### 루틴 블록의 카운트가 두 배로 표시되고 편집 결과가 안무표에 반영되지 않음

커밋 `7d96ec6` · 2026-03-22

**증상** 2×8 루틴을 안무표에 놓으면 8박자 두 줄이 아니라 16카운트짜리 한 덩어리로 들어갔다. 루틴 편집 창에서 행이나 박자 수를 바꿔도 안무표 위의 블록은 그대로였고, 그 블록을 한 번 끌어야 뒤늦게 갱신됐다.

**원인** `placeRoutineOnBoard` 가 여러 행에 걸친 배치를 만드는 공용 헬퍼 `buildSegments` 를 쓰지 않고, `length = rows × cols` 인 배치 하나를 그대로 저장했다. `syncCurrentRoutine` 쪽은 각 세그먼트의 `length` 에 `rows × cols`(총 카운트)를 그대로 넣어, 세그먼트가 둘이면 카운트가 두 배로 계산됐다. 즉 "그룹 전체 카운트"와 "세그먼트 하나의 길이"를 같은 값으로 취급한 것이 원인이다.

**수정** `placeRoutineOnBoard` 가 `buildSegments` 로 행을 넘겨 가며 쪼개 넣도록 바꾸고, `syncCurrentRoutine` 은 `routineId` 별 그룹의 기존 세그먼트를 지운 뒤 앵커 위치에서 새 총 카운트로 다시 `buildSegments` 하고 영향받은 행을 즉시 다시 그리게 했다. 2×8 루틴을 놓아 두 줄로 들어가는지, 편집 창에서 행 수를 바꿨을 때 끌지 않아도 반영되는지로 확인했다.

**재발 방지** 여러 행에 걸친 배치는 반드시 `buildSegments` 한 곳만 거치게 하고, 총 카운트와 세그먼트 길이를 혼동하지 않는다. → [개발 원칙 D-2](PRINCIPLES.md#d-2)(그룹이 원자 단위면 판정도 그룹 단위로)

### 부분 불러오기로 들어온 루틴이 여러 레이어로 흩어지고 이름이 조용히 겹침

커밋 `d5858f8` · 2026-03-22

**증상** 여러 행에 걸친 루틴을 `부분 불러오기` 로 가져오면 행마다 다른 층에 놓여, 하나의 블록이 아니라 계단처럼 흩어져 보였다. 같은 이름의 루틴이 이미 있으면 어느 쪽이 남는지 알 수 없었다.

**원인** 충돌 검사와 층(subRow) 배정을 **세그먼트 단위**로 해서, 같은 `groupId` 의 세그먼트가 행마다 다른 층을 받았다. 정렬 기준도 `startIndex` 하나뿐이라 여러 행에 걸친 그룹의 세그먼트 사이로 다른 배치가 끼어들었다. 루틴 이름 중복 처리 규칙은 아예 없었다.

**수정** 그룹의 **모든 세그먼트가 동시에 들어갈 수 있는 최소 층**을 찾아 전 세그먼트에 같은 값을 배정하고, 정렬 기준을 그룹의 최초 `(row, startIndex)` 로 바꿨다. 이름이 겹치면 `(2)`, `(3)` 을 붙이고 루틴을 즉시 상태에 넣어 다음 중복도 번호를 이어가게 했다. 결과 알림도 세그먼트 개수가 아니라 그룹 개수로 보고하게 바꿨다.

**재발 방지** 그룹이 원자 단위인 데이터는 배치·충돌·정렬 판정을 전부 그룹 단위로 한다. → [개발 원칙 D-2](PRINCIPLES.md#d-2)(그룹이 원자 단위면 배치·충돌·정렬 판정을 전부 그룹 단위로), [D-3](PRINCIPLES.md#d-3)(외부에서 들어온 식별자·이름은 로컬에서 다시 판정)

### 두 겹 이상 쌓인 배치가 행에 잘려 안 보임

커밋 `c8bc579` · 2026-03-22 (3연속 시도)

**증상** 같은 칸에 동작을 두 개 이상 쌓으면 아래층 블록이 행 밖으로 잘려 아예 보이지 않았다.

**원인** 행 높이를 늘리는 방법을 세 번 바꿨다. `15afff7` 은 JS에서 `'calc(1 * var(--cellH) + 6px)'` 문자열을 `style.top` 에 넣었는데 클래스 규칙의 `top:6px` 로 되돌아가 두 층이 겹쳤다. CSS 변수로 옮긴 뒤에도 `29f7ddf` 시점에서 `min-height` 안의 `calc(var() * var())` 산술이 그리드 아이템에서는 신뢰할 수 없었다. 근본 원인은 그 아래 있었다 — `.track` 에 `overflow:hidden` 이 걸려 있고, `position:absolute` 자식은 그리드 행 높이 계산에 전혀 기여하지 않는다.

**수정** in-flow 인 `.track-spacer` div 를 넣고, JS가 `getCellHPx()` 로 잰 실제 px 로 spacer 높이를 `(maxSubRow + 1) × cellH` 로 지정해 행을 물리적으로 밀어내게 했다. 블록의 `top` 도 px 값으로 직접 지정한다. 두 층·세 층을 쌓아 행 높이가 실제로 늘어나는지 눈으로 확인했다.

**재발 방지** absolute 자식은 부모 높이를 만들지 못한다. 높이를 만들어야 하면 in-flow 요소를 쓰거나 컨테이너 높이를 JS에서 명시한다. `calc` 안에서 JS가 만든 문자열로 CSS 변수를 곱하는 방식은 쓰지 않는다. → [개발 원칙 U-8](PRINCIPLES.md#u-8)(내부 스크롤·높이는 조상 체인의 높이 제약을 먼저 확인)

### 쌓아 놓은 동작 중 하나를 옮기면 남은 동작이 위 층으로 올라가 '합쳐진 것처럼' 보임

커밋 `865d9c7` · 2026-03-22 (6연속 시도)

**증상** A(위층)와 B(아래층)를 같은 칸에 쌓아 놓고 A를 다른 곳으로 끌면, B가 위층으로 튀어 올라갔다. 사용자 눈에는 아래층 동작이 사라지고 둘이 하나로 합쳐진 것처럼 보였다.

**원인** "레이어 정체성을 유지할 것인가, 빈 층을 없앨 것인가"가 정해지지 않은 채 여섯 번 뒤집혔다. `2b96a7c` 는 이동 시 원래 층 보존, `f0b7bad` 는 목적지에서 가장 낮은 빈 층 탐색, `4fd6165` 는 `repackSubRows` 로 갭 제거, `28fab32`·`e879d55` 는 데이터는 두고 렌더에서만 압축(공간 기준 → 랭크 기준), `6bf0643` 은 다시 원래 층부터 탐색. 렌더 압축을 하면 남은 B가 시각적으로 0층으로 올라오고, 압축을 안 하면 빈 위층이 남는다 — 이 상충이 계속 왕복했다. 여섯 번 모두 코드를 고쳤을 뿐 어느 쪽이 옳은지를 정하지 않았다.

**수정** 시각적 압축을 완전히 제거하고 `visualSubRow = DATA subRow` 를 그대로 쓰기로 확정했다. B는 혼자 남아도 아래층에 있고 위쪽은 빈 채로 두며, `::after` 구분선으로 층 경계를 보여준다. 트레이드오프(혼자일 때 위쪽에 남는 여백)를 커밋 메시지에 명시해 다음 사람이 되돌리지 않게 했다.

**재발 방지** 같은 현상을 두 번 이상 고치게 되면 코드가 아니라 규칙을 먼저 글로 정하고, 그 규칙을 코드 주석에 고정한다. 여기서 필요했던 규칙은 "데이터 층과 시각 층이 같은가 다른가" 단 하나였다. → [개발 원칙 D-1](PRINCIPLES.md#d-1)(규칙이 갈리는 지점은 코드보다 규칙을 먼저 문서로 확정)

### 같은 프로젝트를 부분 불러오기로 겹쳐 넣으면 두 배치가 한 몸으로 움직임

커밋 `1fe21e6` · 2026-03-22

**증상** 같은 프로젝트에서 파생된 파일을 `부분 불러오기` 로 가져온 뒤 한쪽 블록을 옮기거나 지우면, 화면 반대편의 다른 블록도 같이 움직이거나 사라졌다.

**원인** 들어오는 배치가 원본 파일의 `groupId` 를 그대로 유지해, 이미 보드에 있던 배치의 `groupId` 와 충돌했다. 이동·삭제는 `groupId` 단위로 동작하므로 두 배치가 같은 그룹으로 취급됐다.

**수정** 원본 `groupId` → 새 `groupId` 매핑(`groupIdRemap`)을 만들어 들어오는 모든 배치의 ID를 새로 발급하되, 같은 원본 그룹이면 같은 새 ID를 받아 여러 행 그룹 구조는 유지되게 했다. 같은 파일을 두 번 부분 불러오기 한 뒤 한쪽만 지워지는지로 확인했다.

**재발 방지** 외부에서 들어온 데이터의 식별자는 항상 로컬에서 재발급한다. "그룹 구조 보존"과 "ID 보존"은 다른 문제다. → [개발 원칙 D-3](PRINCIPLES.md#d-3)(외부에서 들어온 식별자는 로컬에서 재발급)

### 블록을 늘리면 아래층 동작이 위층으로 합쳐짐

커밋 `8a8e657` · 2026-03-22

**증상** 아래층에 있던 동작의 길이를 늘려 다음 행까지 넘어가게 하면, 그 동작이 위층 동작과 같은 층에 붙어 보였다.

**원인** `repackSubRows` 가 행별로 독립적으로 층을 재배정하기 때문에, 길이를 늘려 새 행에 세그먼트가 생기면 같은 그룹인데도 행마다 다른 층을 받았다. 행 단위 최적화가 행을 가로지르는 그룹 불변식("같은 그룹은 같은 층")을 깬 것이다.

**수정** 프로젝트·동작·카테고리 세 로더 모두 디스크의 실제 `file.name` 에서 확장자를 뗀 값을 중복 제거 키로 쓰게 했다. 같은 파일의 사본을 이름만 바꿔 열어 두 항목이 나란히 남는지로 확인했다.

**재발 방지** 동일성 판정 키는 파일에 내장된 값이 아니라 외부에서 관찰 가능한 값으로 잡는다. → [개발 원칙 D-6](PRINCIPLES.md#d-6)(동일성 판정 키는 외부에서 관찰 가능한 값으로 잡는다)

### 전체 초기화가 지운 링크가 Undo 로 돌아오지 않음

커밋 병합 전 · 2026-09-07

**증상** `전체 초기화` 를 누르면 안무표의 배치와 함께 링크바의 네 필드(YouTube 주소·제목, ClickUp 주소, 커스텀 링크)가 전부 지워졌다. 곧바로 `Undo` 를 누르면 배치는 돌아오는데 링크는 빈 채였고, 지운 값이 이미 브라우저에 덮어써진 뒤라 새로고침해도 없었다. 버튼은 한 번 누르면 `정말요?` 로 바뀌기만 할 뿐, 배치 말고 무엇이 더 지워지는지 말하지 않았다. 되찾는 방법은 주소를 다시 붙여 넣는 것뿐이었다.

**원인** "무엇이 상태인가"의 답이 두 곳에서 달랐다. `0c44d3f`(PR #17)가 `clearBoard()` 의 정리 범위를 배치에서 링크까지 넓히고 `saveLinks()` 로 localStorage 에 즉시 반영하게 했는데, 되돌리기 스냅샷을 만드는 필드 목록 `UNDO_FIELDS` 는 `rows`·`cols`·`placements`·`moveLibrary`·`categories`·`routines` 여섯뿐이었다. 반면 프로젝트 파일의 필드 목록 `DOC_FIELDS` 에는 링크가 들어 있었다 — 파일은 링크를 상태로 보고 undo 는 아니라고 본 것이다. 정리 범위를 넓히면서 그것을 되돌리는 장치(스냅샷 필드, 확인 문구) 쪽을 함께 넓히지 않은 [R-4](PRINCIPLES.md#r-4) 의 세 번째 사례였다. 링크 편집 자체도 히스토리를 쌓지 않아서, 주소를 고친 뒤 다른 조작을 하고 `Undo` 하면 링크까지 딸려 되돌아가는 짝 결함이 있었다.

**수정** 링크를 Undo 범위에 넣었다. `전체 초기화` 가 링크를 지우는 동작은 의도된 것이라 유지하고 "되돌릴 수 없다"만 없앴다. `UNDO_FIELDS` 맨 뒤에 `links` 를 더해 `DOC_FIELDS` 와 같은 집합으로 만들고(루틴 보드에는 링크가 없으므로 `ROUTINE_UNDO_FIELDS` 는 3필드 그대로), 링크가 `customLinks` 배열을 품은 중첩 객체인 점을 `snapshot.toLinkBundle` 한 자리로 흡수했다 — 스냅샷을 뜰 때는 값 복제라 store 와 배열을 공유하지 않고, 되돌릴 때는 키가 없는 옛 스냅샷도 빈 4필드로 채운다. 상태만 되돌리면 새로고침에서 지워진 값이 되살아나므로 `createHistory(store, { storage })` 가 `saveLinks` 를 주입받아 복원 직후 같은 키(`choreo_links`)에 되쓴다. 복원 Dirty 에 `links` 를 켜 입력창이 옛 값을 들고 남지 않게 하고, 제목 조회 중에 Undo 했을 때 스피너가 영영 남던 것도 같은 자리에서 막았다. 링크 편집의 히스토리 커밋 지점은 `ui/linksBarView.js` 가 소유하고 여섯 자리로 한정했다 — 두 URL 입력창의 `change`(blur/Enter), `✕` 초기화 둘, 커스텀 링크의 추가·삭제·레이블/URL `change`. `input` 과 제목 조회 착지에는 걸지 않았다. 확인 문구는 버튼 라벨을 `전체 초기화(링크 포함)` 로 바꿔 드러냈다.

**재발 방지** 상태의 정의를 한 곳에만 둔다 — `domain/project/schema.js` 의 필드 목록이 그 한 곳이고, undo 스냅샷과 파일 포맷이 같은 집합을 본다. 파괴적 함수의 정리 범위를 넓히는 diff 는 스냅샷 필드와 확인 문구를 같은 커밋에서 함께 넓혔는지 확인한다. 골든 150개는 undo/redo 를 다루지 않으므로 안전망은 단위 테스트다 — `tests/unit/domain.test.mjs` 에 링크 × undo 13개를 심었고, 그중 하나는 `index.html` 의 `#clearBtn` 글자와 `CLEAR_BTN_LABEL` 이 같은지를 대조한다(둘이 어긋나면 확인 뒤 버튼 이름이 조용히 바뀐다). → [개발 원칙 D-4](PRINCIPLES.md#d-4)(저장 스키마는 한 곳에 정의하고 세 경로를 함께 고친다), [R-4](PRINCIPLES.md#r-4)(파괴적 헬퍼는 정리 범위를 되돌리는 장치도 함께 넓힌다)

이 수정을 검증하는 테스트를 쓰다 별개의 결함이 드러났다 — 메인 `Undo` 직후의 커밋이 유령 단계를 만들고 Redo 스택을 날린다. 원인이 카테고리 정규화의 정렬이라 이 커밋 소관이 아니어서 고치지 않고 특성화 테스트로 못박았다. [일부러 두고 온 것](deviations.md#저장과-복원의-비대칭) 에 등록돼 있다.

### 모바일에서 크기 조절 핸들이 첫 터치에 반응하지 않음

### HTTPS가 아닌 환경에서 Dropbox 로그인 버튼이 아무 반응 없음

## 아직 남아 있는 위험

아래 항목은 모두 재구성 이전 `index.html`(5,289줄, `f86f991` 기준)에서 직접 확인한 것이다. 인용한 줄 번호는 전부 그 파일 기준이다 — 지금 `index.html` 은 1,387줄짜리 마크업만 남았고 그 코드는 `src/` 아래 ES 모듈로 옮겨졌다. 확인되지 않은 항목은 이 목록에서 제외했다.

각 항목 끝에는 `index.html` 을 `src/` 아래 ES 모듈로 재구성한 작업이 그 위험을 없앴는지를 한 줄로 붙였다. 루틴 색과 글자색 대비 두 항목은 2026-09-07 에 고쳐서 이 목록에서 빠졌고, 정식 버그 항목으로 [눈으로 상태를 구분할 수 없다](#눈으로-상태를-구분할-수-없다)에 옮겨 적었다. `전체 초기화` 가 지운 링크가 Undo 로 돌아오지 않던 항목도 같은 날 고쳐서 [다시 열면 달라진다](#다시-열면-달라진다)로 옮겼다. 같은 날 **리사이즈만 다른 동작을 조용히 지우던 항목**도 닫혀 [겹치거나 여러 행에 걸친 동작이 어긋난다](#크기를-늘려-겹치면-리사이즈만-그-동작을-통째로-지움)로 옮겼다 — 이 목록에서 "재구성 후에도 남음"으로 분류했던 것 중 처음으로 닫힌 항목이고, 분류대로 모듈을 나눈 것이 아니라 규칙을 정한 것이 답이었다. 아직 남은 것의 지금 위치와 고칠 때 함께 해야 할 일은 [일부러 두고 온 것](deviations.md)에 있다. 판단 기준은 셋이다 — 규칙이 여러 곳에 흩어져 생긴 문제거나 순수한 복제면 합치는 과정에서 사라지므로 **재구성에서 해소됨**, 무엇이 옳은 동작인지를 먼저 정해야 하는 문제면 옮기는 것만으로는 답이 나오지 않으므로 **재구성 후에도 남음**, 상수 하나·조건 하나처럼 위치와 무관하게 따라오는 문제면 **재구성이 건드리지 않음** 이다.

### copyPlacementGroup 만 층 재정렬을 부르지 않는다

`removePlacementGroup`(index.html:3574), `movePlacementGroup`(:3665), `rebuildGroup`(:3724) 은 모두 `repackSubRows` 를 호출하는데, `copyPlacementGroup`(:3673~3705) 에만 빠져 있다. Alt+드래그 복사 뒤에는 `78909f8` 이 고친 "빈 상단 레이어가 남는" 상태가 그대로 재현될 수 있다.

**재구성에서 해소됨.** 네 경로가 같은 후처리를 해야 하는데 한 곳만 빠뜨린 단순 누락이다. 이동·복사·삭제·크기 조절을 한 모듈에 모으고 층 재정렬을 공통 후처리로 빼면 누락 자체가 성립하지 않는다.

### renderRow 의 주석과 실제 동작이 어긋난다

`index.html:3369-3370` 에 `865d9c7` 의 결론이 주석으로 남아 있다.

```
// 시각적 subRow = DATA subRow 그대로 사용 (압축 없음)
// → 하위 레이어 배치는 혼자 있어도 항상 하단에 위치 (레이어 정체성 보존)
```

그런데 `78909f8` 이 이동 후 `repackSubRows` 로 다시 압축하도록 바꿨다. 레이어 정체성 유지 여부는 `2b96a7c → f0b7bad → 6bf0643 → 78909f8` 로 네 번 뒤집혔고, 확정된 규칙이 코드 어디에도 없다. 이 주석을 믿고 고치면 다섯 번째 왕복이 된다.

**재구성 후에도 남음.** 주석과 코드가 서로 다른 규칙을 말하는 상태는 규칙을 한 곳으로 모으면 드러나지만, "이동할 때 층을 유지하는가 낮추는가"라는 답 자체는 별도 결정이다. 결정 없이 옮기면 새 구조에 같은 모순이 그대로 이사한다.

### 모바일 확대가 전면 차단돼 있고 포커스 해제 때 페이지가 최상단으로 튄다

viewport 에 `maximum-scale=1.0, user-scalable=no` 가 걸려 있고(index.html:5), `focusout` 마다 viewport 를 다시 세팅한 뒤 `window.scrollTo(0, 0)` 을 호출한다(:1664-1676). `2000580` 의 iOS 자동 확대 회피용 임시방편인데, 안무표 아래쪽에서 입력하고 손을 떼면 화면이 맨 위로 올라간다. 게다가 짝이 되던 `input { font-size: 16px !important }` 규칙은 `c297e19` 가 지워서 현재 파일에 `16px !important` 는 하나도 없고, 그 자리에는 주석만 남아 있다(:638).

**재구성이 건드리지 않음.** viewport 메타와 `focusout` 보정을 유지할지 되돌릴지는 플랫폼 대응 정책 결정이다. 다만 재구성 때 이 조치와 짝이던 `font-size` 규칙이 사라졌다는 사실은 함께 기록해 둬야 한다.

### 동작을 한 번 옮길 때마다 보드 전체를 다시 그린다

`renderBoard`(index.html:3334-3336), `movePlacementGroup`(:3668-3669), `copyPlacementGroup`(:3701-3702), `finishTouchPlacementMove`(:3887-3888) 이 모두 `[0, ...1..rows]` 전체를 `renderRows` 에 넘긴다. `a3d5d5c` 에서 잔상 회피용으로 도입하고 `cc590a7` 이 row 0 을 덧붙인 결과다. `renderRow` 단위의 부분 렌더 구조가 사실상 무력화돼 있고, 같은 행 범위 생성 표현식이 네 군데에 복붙돼 있다.

**재구성 후에도 남음.** 네 군데에 복붙된 행 범위 표현식은 헬퍼로 합치면 사라지지만, "부분 렌더로 돌아갈 것인가 전체 렌더를 규칙으로 못 박을 것인가"는 층 계산을 행 안에 가둘 수 있느냐에 달린 별도 결정이다.

### 최근 프로젝트 10개의 payload 전체를 localStorage 에 넣으면서 예외 처리가 없다

```
index.html:4042  state.savedFiles = [{ fileName, savedAt: payload.savedAt, data: payload }, ...state.savedFiles.filter(f => f.fileName !== fileName)].slice(0, 10);
index.html:4043  localStorage.setItem('choreo_saved_files', JSON.stringify(state.savedFiles));
```

`a86b336` 에서 5개 → 10개로 늘렸는데, 항목마다 배치·동작·카테고리·루틴이 통째로 들어간다. 용량이 차면 `QuotaExceededError` 가 나면서 저장 함수가 `renderSavedList()` 전에 중단되고, 사용자에게는 아무 안내도 가지 않는다. 읽기 쪽(:4195-4199)에만 try/catch 가 있다. 같은 형태의 무방비 `setItem` 이 :4279, :4399, :4418 에도 있다.

**재구성에서 해소됨.** 저장소 접근을 한 모듈로 모으면서 쓰기 경로에 `try`/`catch` 와 사용자 안내를 넣으면 네 군데의 무방비 `setItem` 이 한 번에 정리된다. 다만 항목 상한 10개와 payload 통째 저장을 유지할지는 별도로 봐야 한다.

### 메인 보드와 루틴 편집기의 빠른 배치 팝업 로직이 복제돼 있다

메인 보드는 `closeQuickPicker`(:1776) / `openQuickPicker`(:1808), 루틴 편집기는 `closeReQuickPicker`(:4774) / `openReQuickPicker`(:4898) 로 두 벌이 따로 있다. `8f80666` 이 메인 보드만 고쳐 `227af3d` 로 따로 고쳐야 했던 자리이고, 두 경로는 지금도 나뉘어 있다. 실제로 이미 다시 벌어졌다 — `+` 버튼 하이라이트를 붙인 `997ec83`(PR #15)의 `addBtn.classList.toggle('kb-active', !exactExists)` 가 메인 보드(:1931)에만 있고 루틴 편집기(:4959-4960)에는 없다.

**재구성에서 해소됨.** 순수한 복제 문제다. 두 경로가 `ctx` 만 다르므로 팝업을 하나의 모듈로 합치면 `kb-active` 처럼 이미 벌어진 차이도 함께 없어진다.

### 카테고리 정렬에서 카테고리가 없는 동작이 항상 맨 앞으로 간다

PR #17 이 추가한 `카테고리` 정렬은 카테고리 이름의 삽입 순서를 `indexOf` 로 찾아 비교한다(index.html:4241-4246). 카테고리가 삭제됐거나 비어 있는 동작은 `indexOf` 가 -1 을 반환하므로, 오름차순에서 모든 실제 카테고리보다 앞에 놓인다.

**재구성이 건드리지 않음.** 정렬 함수를 어느 모듈에 두든 `indexOf` 의 -1 은 그대로 따라간다. 재구성과 무관하게 별도로 고쳐야 한다.
